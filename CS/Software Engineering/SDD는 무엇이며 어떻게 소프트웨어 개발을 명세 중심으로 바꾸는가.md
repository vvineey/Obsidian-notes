# SDD는 무엇이며 어떻게 소프트웨어 개발을 명세 중심으로 바꾸는가?

## 1. SDD의 정의와 등장 배경

### SDD란?

SDD(Spec-Driven Development)는 **코드를 작성하기 전에 요구사항과 제약 조건을 명확한 명세로 만들고, 그 명세를 기준으로 설계·작업·코드·테스트를 생성하고 검증하는 개발 방식**이다.

쉽게 말하면 다음과 같다.

> “일단 코드를 만들고 나중에 문서화하는 것”이 아니라,  
> “무엇을 만들어야 하는지 먼저 합의하고 그 명세를 따라 코드를 만드는 것”이다.

전통적인 개발에서는 요구사항 문서가 구현을 위한 참고 자료로 사용되다가, 개발이 시작되면 코드가 사실상의 기준이 되는 경우가 많았다.

SDD는 이 관계를 반대로 본다.

> 명세가 코드를 보조하는 것이 아니라, 코드가 명세를 구현한다.

따라서 SDD에서 명세는 단순한 설명 문서가 아니다. 요구사항, 설계, 작업 분해, 테스트와 구현을 연결하는 중심 자료다.

| 산출물 | 답해야 하는 질문 |
| --- | --- |
| 요구사항 명세 | 무엇을 만들어야 하는가? |
| 인수 조건 | 언제 요구사항을 만족했다고 판단하는가? |
| 기술 설계 | 어떤 구조와 기술로 구현하는가? |
| 작업 목록 | 어떤 순서로 구현하는가? |
| 코드와 테스트 | 실제 구현이 명세를 만족하는가? |

### 좋은 명세의 예

“로그인 기능을 만들어야 한다”는 문장만으로는 부족하다.

다음처럼 검증할 수 있는 조건이 들어가야 한다.

- 사용자는 이메일과 비밀번호로 로그인할 수 있다.
- 잘못된 비밀번호를 연속 5회 입력하면 계정을 10분간 잠근다.
- 로그인 성공 시 30분 동안 유효한 세션을 발급한다.
- 존재하지 않는 계정과 잘못된 비밀번호는 외부에서 구분되지 않는 오류를 반환한다.

이렇게 작성해야 개발자와 AI가 같은 완료 조건을 바라볼 수 있다.

### 등장 배경 1: 문서와 코드의 불일치

기존 개발에서도 요구사항과 설계 문서를 작성했다. 하지만 구현이 변경될 때 문서가 함께 갱신되지 않으면 다음 문제가 발생한다.

- 요구사항에는 있지만 코드에는 없는 기능
- 코드에는 있지만 문서화되지 않은 동작
- 변경된 요구사항이 테스트에 반영되지 않는 문제
- 설계 이유가 남지 않아 유지보수가 어려워지는 문제

SDD는 명세를 일회성 문서가 아니라 지속적으로 관리하는 핵심 산출물로 취급하여 이러한 불일치를 줄이려 한다.

### 등장 배경 2: 모호한 요구사항

개발 실패의 원인은 코딩 능력 부족만이 아니다.

요구사항을 기획자, 개발자, 사용자가 서로 다르게 이해하면 기술적으로 완성된 코드를 작성해도 잘못된 제품이 만들어질 수 있다.

SDD는 구현을 시작하기 전에 다음 내용을 명확하게 만든다.

- 기능의 범위
- 완료 조건
- 예외 상황
- 성능과 보안 요구사항
- 기술적 제약
- 이번 작업에서 제외되는 범위

수정 비용이 큰 구현 단계에 들어가기 전에 요구사항의 오류를 찾는 것이 목적이다.

### 등장 배경 3: AI 코딩 에이전트의 확산

최근 SDD가 특히 주목받는 이유는 AI 코딩 에이전트 때문이다.

AI에게 모호한 문장 하나만 주고 바로 코드를 작성하게 하면, AI는 빠진 내용을 스스로 추측한다.

그 결과 다음과 같은 문제가 발생할 수 있다.

- 요구하지 않은 기능을 추가한다.
- 중요한 예외 처리를 빠뜨린다.
- 기존 아키텍처와 맞지 않는 기술을 사용한다.
- 긴 대화 중 초기 요구사항을 잃어버린다.
- 동작하는 코드가 실제 요구사항을 만족하는지 알기 어렵다.

SDD는 AI에게 단순한 채팅 기록 대신 구조화된 요구사항, 기술 설계, 작업 목록을 제공한다.

즉, AI를 단순 코드 생성기가 아니라 **명세를 분석하고 구현하는 협업 도구**로 활용하는 방식이다.

다만 SDD는 현재 하나의 표준 기관이 정의한 고정 방법론이라기보다 GitHub Spec Kit, Kiro, OpenSpec 같은 도구들이 공통된 철학을 각자의 방식으로 구현하고 있는 단계에 가깝다.

## 2. SDD의 핵심 원칙과 워크플로우

### 핵심 원칙 1: 명세가 기준 정보다

SDD에서는 요구사항과 구현이 충돌할 때 판단 기준이 되는 자료가 명세다.

기능이 변경되면 코드만 수정하는 것이 아니라 다음 순서로 변경한다.

1. 요구사항 명세를 수정한다.
2. 영향을 받는 기술 설계를 확인한다.
3. 구현 작업과 테스트를 수정한다.
4. 마지막으로 코드를 변경한다.

### 핵심 원칙 2: 완료 조건을 검증할 수 있어야 한다

명세에는 무엇을 만들 것인지뿐 아니라 언제 완성됐다고 판단할 것인지도 포함해야 한다.

이를 위해 다음과 같은 요소를 사용한다.

- 사용자 스토리
- 기능 요구사항
- 비기능 요구사항
- 인수 조건
- Given-When-Then 시나리오
- 오류 및 경계 조건
- 포함 범위와 제외 범위

예를 들어 “검색이 빨라야 한다”는 요구사항은 검증하기 어렵다.

“상품 10만 건에서 검색 요청의 95%가 500ms 이내에 완료되어야 한다”처럼 작성해야 실제 테스트가 가능하다.

### 핵심 원칙 3: 요구사항부터 테스트까지 추적할 수 있어야 한다

SDD에서는 다음 관계가 연결돼야 한다.

```text
요구사항
  ↓
인수 조건
  ↓
기술 설계
  ↓
구현 작업
  ↓
코드와 테스트
```

특정 요구사항이 변경됐을 때 영향을 받는 설계, 작업, 코드와 테스트를 찾을 수 있어야 한다.

이러한 연결을 요구사항 추적성이라고 한다.

### 핵심 원칙 4: 명세도 반복적으로 개선한다

SDD는 처음부터 완벽한 문서를 작성하고 그대로 구현하는 폭포수 방식이 아니다.

구현 중 새로운 기술적 제약이 발견되거나 사용자 피드백이 들어오면 명세를 수정할 수 있다.

중요한 것은 변경 내용을 채팅이나 개인의 기억에만 남기지 않고 명세에도 반영하는 것이다.

### 핵심 원칙 5: 명세와 구현을 모두 검증한다

명세가 존재한다고 해서 구현이 자동으로 올바른 것은 아니다.

다음 두 가지를 모두 검증해야 한다.

1. 명세 자체에 모순, 누락, 모호함이 없는가?
2. 구현과 테스트가 실제로 명세를 만족하는가?

따라서 코드 리뷰뿐 아니라 명세 리뷰도 필요하다.

### 핵심 원칙 6: 중요한 판단은 사람이 승인한다

AI가 요구사항, 설계와 작업 목록을 생성하더라도 다음 항목은 사람이 검토해야 한다.

- 실제 사용자의 요구를 정확히 반영했는가?
- 보안과 개인정보 보호 조건이 충분한가?
- 아키텍처가 운영 환경에 적합한가?
- 생성된 테스트가 핵심 요구사항을 검증하는가?
- 명세 자체에 잘못된 가정이 없는가?

AI는 누락과 모호함을 찾는 데 도움을 주지만, 제품의 목적과 위험에 대한 최종 책임까지 대신할 수는 없다.

### 일반적인 SDD 워크플로우

#### 1단계: 문제와 의도 정의

구현할 코드보다 먼저 해결해야 할 문제를 정의한다.

- 사용자는 누구인가?
- 어떤 문제가 있는가?
- 왜 이 기능이 필요한가?
- 이번 작업에 포함되지 않는 것은 무엇인가?

#### 2단계: 요구사항 명세 작성

아이디어를 구체적인 요구사항과 인수 조건으로 변환한다.

예를 들어 비밀번호 재설정 기능은 다음과 같이 표현할 수 있다.

- 가입된 이메일로 재설정을 요청하면 일회용 링크를 발송한다.
- 링크는 30분 동안만 유효하다.
- 만료됐거나 이미 사용한 링크로는 비밀번호를 변경할 수 없다.
- 요청한 이메일의 가입 여부가 외부에 노출되지 않아야 한다.

#### 3단계: 명세 검토와 명확화

명세에서 다음 문제를 찾는다.

- 모호한 표현
- 서로 충돌하는 조건
- 빠진 예외 상황
- 검증할 수 없는 완료 조건
- 숨겨진 보안 및 성능 요구사항

#### 4단계: 기술 설계 작성

요구사항을 실제로 구현할 수 있는 구조로 변환한다.

- 시스템 구성 요소
- 데이터 모델
- API 계약
- 데이터 흐름
- 외부 시스템 연동
- 오류 처리
- 인증과 권한
- 성능 및 운영 고려사항
- 기술 선택과 선택 이유

요구사항이 “무엇을 만들 것인가”에 가깝다면 기술 설계는 “어떻게 만들 것인가”에 가깝다.

#### 5단계: 작업 분해

설계를 작고 검증 가능한 구현 작업으로 나눈다.

좋은 작업은 다음 조건을 만족한다.

- 관련 요구사항을 찾을 수 있다.
- 완료 여부를 명확히 판단할 수 있다.
- 선행 작업과 의존성이 표시된다.
- 코드와 테스트가 함께 고려된다.
- 한 작업의 범위가 지나치게 크지 않다.

#### 6단계: 구현과 테스트

개발자 또는 AI가 작업 목록에 따라 구현한다.

각 작업이 완료될 때 테스트를 실행하고 명세의 인수 조건을 만족하는지 확인한다.

TDD와 함께 사용한다면 인수 조건을 기반으로 실패하는 테스트를 먼저 작성하고, 해당 테스트를 통과시키는 코드를 구현할 수 있다.

#### 7단계: 일관성 검증

다음 항목을 확인한다.

- 모든 요구사항에 구현 작업이 존재하는가?
- 모든 인수 조건이 테스트되고 있는가?
- 기술 설계와 실제 구현이 일치하는가?
- 요구사항에 없는 기능이 임의로 추가되지 않았는가?
- 성능과 보안 같은 비기능 요구사항도 검증됐는가?

#### 8단계: 변경 관리

운영 중 발생한 사용자 피드백, 장애, 성능 문제와 보안 취약점을 새로운 요구사항이나 제약으로 반영한다.

```text
운영 피드백
  → 명세 변경
    → 영향 분석
      → 설계·작업·테스트 수정
        → 구현 변경
```

## 3. SDD의 장점과 한계

### 장점

| 장점 | 설명 |
| --- | --- |
| 요구사항 명확화 | 구현 전에 모호함, 충돌, 누락을 발견할 수 있다. |
| 예측 가능한 AI 활용 | AI가 추측하지 않고 구조화된 명세를 기준으로 작업한다. |
| 추적성 | 요구사항이 어떤 설계, 작업, 코드와 테스트로 이어졌는지 확인할 수 있다. |
| 검토 가능성 | 코드를 작성하기 전에 요구사항과 아키텍처를 팀이 검토할 수 있다. |
| 컨텍스트 유지 | 대화나 담당자가 바뀌어도 명세를 통해 개발 의도를 전달할 수 있다. |
| 유지보수성 | 기술 선택과 설계 이유가 남아 변경 영향 분석에 도움이 된다. |
| 테스트 설계 | 구체적인 인수 조건을 테스트 케이스로 변환하기 쉽다. |
| 협업 | 합의된 인터페이스와 작업 경계를 바탕으로 업무를 나눌 수 있다. |

### 한계

| 한계 | 설명 |
| --- | --- |
| 초기 비용 | 코딩 전에 명세를 작성하고 검토하는 시간이 필요하다. |
| 명세 품질 의존 | 잘못된 명세를 정확하게 구현하면 결과도 정확하게 잘못된다. |
| 동기화 비용 | 코드 변경 시 명세를 함께 수정하지 않으면 다시 불일치가 발생한다. |
| 과도한 형식화 | 모든 결정을 미리 고정하면 실험과 탐색이 어려워질 수 있다. |
| AI의 허위 완전성 | AI가 만든 상세한 문서가 완전하고 정확하다는 착각을 줄 수 있다. |
| 도구 종속성 | 특정 IDE, 명령어와 디렉터리 구조에 워크플로우가 묶일 수 있다. |
| 검증의 어려움 | 성능과 보안 요구사항은 문서화만으로 보장되지 않는다. |
| 기존 프로젝트 적용 | 레거시 시스템은 현재 동작을 명세로 복원하는 작업부터 필요하다. |

### SDD가 적합한 작업

- 여러 시스템이 연동되는 기능
- 결제, 인증, 권한처럼 위험이 큰 기능
- 요구사항 누락의 비용이 큰 기능
- 여러 개발자나 AI 에이전트가 함께 작업하는 프로젝트
- 장기간 유지보수해야 하는 시스템

### SDD가 과할 수 있는 작업

- 오타 수정
- 단순한 스타일 변경
- 범위가 명확한 작은 버그 수정
- 버리고 다시 만들 수 있는 짧은 실험 코드

따라서 모든 작업에 동일한 크기의 명세를 작성해서는 안 된다. 작업의 복잡도와 위험에 맞게 명세의 깊이를 조절해야 한다.

## 4. 대표적인 SDD 프레임워크

### 1) GitHub Spec Kit

GitHub가 공개한 오픈소스 SDD 툴킷이다. 여러 AI 코딩 에이전트와 함께 사용할 수 있다.

대표 흐름은 다음과 같다.

```text
Constitution
  → Specify
    → Clarify
      → Plan
        → Tasks
          → Analyze
            → Implement
```

- Constitution: 프로젝트의 공통 원칙과 품질 기준 정의
- Specify: 기능 요구사항과 인수 조건 작성
- Clarify: 모호하거나 누락된 요구사항 보완
- Plan: 기술 스택과 아키텍처를 포함한 구현 계획 작성
- Tasks: 실행할 수 있는 작업 목록으로 분해
- Analyze: 명세, 계획과 작업 사이의 일관성 검사
- Implement: 작업 목록에 따라 코드 구현

장점은 단계별 산출물과 검토 지점이 명확하다는 것이다.

반면 작은 기능에는 생성해야 하는 문서와 절차가 무겁게 느껴질 수 있다.

### 2) Kiro Specs

Kiro는 AWS가 개발한 AI 개발 환경이다. IDE, CLI와 웹에서 명세 기반 개발 흐름을 제공한다.

주요 산출물은 다음과 같다.

```text
requirements.md
  → design.md
    → tasks.md
      → implementation
```

- `requirements.md`: 사용자 스토리와 인수 조건
- `design.md`: 아키텍처와 구현 방법
- `tasks.md`: 의존성을 고려한 구현 작업 목록

일반적인 기능 개발뿐 아니라 버그 수정과 빠르게 명세를 만드는 Quick Spec 같은 흐름도 지원한다.

계획부터 구현까지 개발 환경에 통합돼 있다는 장점이 있지만, Kiro 환경에 대한 의존성이 생길 수 있다.

### 3) OpenSpec

OpenSpec은 여러 AI 코딩 도구와 함께 사용할 수 있는 비교적 가벼운 오픈소스 SDD 프레임워크다.

대표 흐름은 다음과 같다.

```text
Explore
  → Propose
    → Apply
      → Verify
        → Archive
```

일반적으로 변경 단위마다 다음 자료를 관리한다.

- `proposal.md`: 변경 이유와 범위
- `specs/`: 요구사항과 구체적인 시나리오
- `design.md`: 기술적 접근 방법
- `tasks.md`: 구현 체크리스트

OpenSpec은 작업이 끝나면 변경 사항을 현재 시스템 명세에 반영하고 완료된 변경 기록을 보관한다.

상대적으로 가볍고 기존 프로젝트에 점진적으로 적용하기 좋다. 다만 팀의 승인 규칙과 명세 품질 기준은 별도로 정해야 한다.

### 프레임워크 비교

| 구분 | GitHub Spec Kit | Kiro Specs | OpenSpec |
| --- | --- | --- | --- |
| 형태 | 오픈소스 툴킷·CLI | 통합 AI 개발 환경 | 경량 오픈소스 CLI |
| 기본 흐름 | Spec → Plan → Tasks → Implement | Requirements → Design → Tasks → Execute | Propose → Apply → Verify → Archive |
| 핵심 특징 | 체계적인 단계와 프로젝트 원칙 | 계획부터 구현까지 개발 환경에 통합 | 변경 단위 관리와 유연한 반복 |
| 적합한 경우 | 명확한 절차와 거버넌스가 필요할 때 | 하나의 환경에서 전체 과정을 진행할 때 | 기존 도구를 유지하며 가볍게 도입할 때 |
| 주의점 | 작은 작업에는 무거울 수 있음 | 도구 종속성이 상대적으로 큼 | 팀별 규칙을 직접 정해야 함 |

## 헷갈리기 쉬운 지점

### SDD는 단순한 문서화가 아니다

일반적인 문서는 이미 만들어진 코드의 구조와 사용법을 설명할 수 있다.

SDD의 명세는 아직 만들지 않은 기능의 요구사항을 정의하고, 이후 설계·작업·코드·테스트를 이끄는 기준으로 사용된다.

### SDD는 폭포수 모델과 같지 않다

폭포수 모델은 요구사항, 설계, 구현, 테스트 단계를 순차적으로 완료하는 프로젝트 관리 방식이다.

SDD도 구현 전에 요구사항을 다루지만, 구현 중 발견한 문제를 다시 명세에 반영하는 반복적인 흐름을 허용한다.

다만 승인 단계를 지나치게 경직되게 운영하면 실제로는 폭포수 방식처럼 변질될 수 있다.

### SDD와 TDD는 경쟁 관계가 아니다

| 구분 | 핵심 질문 |
| --- | --- |
| SDD | 무엇을 왜 만들어야 하며 전체 구현이 명세와 일치하는가? |
| TDD | 작은 동작을 테스트로 어떻게 정의하고 구현할 것인가? |
| BDD | 사용자의 행동과 결과를 어떤 시나리오로 표현할 것인가? |

SDD의 인수 조건을 BDD 시나리오로 표현하고, 세부 구현 과정에서는 TDD를 적용할 수 있다.

## 꼬리 질문과 답변

### 1. SDD의 정의와 등장 배경을 설명해주세요.

**답변**

SDD는 구현보다 먼저 요구사항과 제약을 명세로 만들고, 그 명세를 기준으로 설계, 작업, 코드와 테스트를 생성하고 검증하는 개발 방식입니다.

기존 개발에서는 요구사항 문서와 실제 코드가 쉽게 달라졌고, AI 코딩에서는 모호한 프롬프트를 받은 AI가 누락된 조건을 임의로 추측하는 문제가 발생했습니다. SDD는 명세를 기준 정보로 관리하고 AI에게 구조화된 요구사항과 설계를 제공하여 의도와 구현의 차이를 줄이기 위해 주목받았습니다.

다만 현재 SDD는 하나의 공식 표준이라기보다 GitHub Spec Kit, Kiro와 OpenSpec 등이 각자의 방식으로 구현하고 있는 개발 철학과 실천 방식에 가깝습니다.

### 2. SDD의 핵심 원칙과 워크플로우를 설명해주세요.

**답변**

핵심 원칙은 명세를 개발의 기준으로 삼고, 요구사항부터 코드와 테스트까지 추적 가능하게 연결하며, 명세와 구현을 반복적으로 검증하는 것입니다.

일반적인 워크플로우는 다음과 같습니다.

1. 해결할 문제와 범위를 정의합니다.
2. 요구사항과 인수 조건을 작성합니다.
3. 모호함, 충돌과 누락을 검토합니다.
4. 요구사항을 바탕으로 기술 설계를 작성합니다.
5. 설계를 구현 가능한 작업으로 분해합니다.
6. 작업별로 코드와 테스트를 작성합니다.
7. 구현이 모든 요구사항을 만족하는지 검증합니다.
8. 변경이나 운영 피드백이 발생하면 명세부터 갱신합니다.

AI가 명세를 만들더라도 요구사항과 아키텍처 같은 중요한 결정은 사람이 검토해야 합니다.

### 3. SDD의 장점과 한계를 설명해주세요.

**답변**

SDD의 장점은 구현 전에 요구사항의 모호함과 누락을 발견할 수 있다는 것입니다. AI도 추측에 의존하지 않고 구조화된 명세를 기준으로 작업하게 됩니다. 요구사항, 설계, 작업, 코드와 테스트 사이의 추적성이 높아져 리뷰와 유지보수에도 도움이 됩니다.

반면 명세 작성과 검토에 초기 비용이 필요합니다. 명세 자체가 잘못되면 구현도 잘못될 수 있으며, 코드가 변경될 때 명세를 함께 갱신하지 않으면 다시 불일치가 발생합니다. 작은 작업에 무거운 절차를 적용하면 오히려 생산성이 떨어질 수도 있습니다.

따라서 작업의 복잡도와 위험에 따라 명세의 깊이를 조절하고, AI가 작성한 명세도 사람이 검증해야 합니다.

### 4. SDD 프레임워크를 소개해주세요.

**답변**

대표적인 도구로는 GitHub Spec Kit, Kiro Specs와 OpenSpec이 있습니다.

GitHub Spec Kit은 명세, 계획, 작업, 구현으로 이어지는 체계적인 흐름을 제공하고 프로젝트의 공통 원칙도 관리할 수 있습니다. 구조적인 대신 작은 작업에는 다소 무거울 수 있습니다.

Kiro Specs는 요구사항, 설계, 작업 목록을 만든 뒤 구현하는 과정을 IDE, CLI와 웹에 통합합니다. 계획부터 실행까지 연결하기 편하지만 Kiro 환경에 대한 의존성이 생길 수 있습니다.

OpenSpec은 변경마다 제안서, 명세, 설계와 작업 목록을 관리하는 비교적 가벼운 오픈소스 도구입니다. 기존 AI 코딩 도구와 함께 사용하기 편하지만, 팀별 승인과 품질 규칙은 직접 정해야 합니다.

### 5. SDD와 TDD의 차이는 무엇인가요?

**답변**

SDD는 시스템이나 기능 수준에서 무엇을 왜 만들고, 구현 전체가 명세를 만족하는지를 관리합니다. 반면 TDD는 작은 단위의 동작을 실패하는 테스트로 먼저 정의한 뒤 그 테스트를 통과시키는 코드를 작성하는 구현 기법입니다.

따라서 둘은 대체 관계가 아닙니다. SDD에서 만든 요구사항과 인수 조건을 상위 기준으로 사용하고, 각각의 구현 작업에서는 TDD를 적용할 수 있습니다. SDD가 방향과 완료 조건을 정한다면 TDD는 세부 구현을 안전하게 진행하는 방법이라고 볼 수 있습니다.

### 6. SDD가 폭포수 모델로 변질되지 않으려면 어떻게 해야 하나요?

**답변**

명세를 구현 전에 한 번 확정하고 다시는 바꾸지 않는 문서로 보면 폭포수 방식처럼 경직될 수 있습니다. 이를 방지하려면 명세를 변경 가능한 버전 관리 산출물로 취급해야 합니다.

구현 과정에서 기술적 제약이나 새로운 요구사항이 발견되면 명세와 설계를 다시 수정하고, 영향받는 작업과 테스트를 갱신해야 합니다. 또한 작은 변경에는 가벼운 명세를 사용하고, 위험이 큰 변경에만 상세한 검토 절차를 적용하는 것이 좋습니다. 핵심은 단계를 엄격히 고정하는 것이 아니라 명세와 구현 사이의 피드백 루프를 유지하는 것입니다.

### 7. SDD를 적용했는데도 잘못된 결과가 나온다면 무엇을 확인해야 하나요?

**답변**

먼저 명세 오류와 구현 오류를 분리해야 합니다. 명세가 실제 사용자의 요구를 잘못 표현했다면 구현이 명세와 일치해도 제품은 잘못될 수 있습니다.

명세가 올바르다면 각 요구사항이 설계와 작업에 연결됐는지, 인수 조건이 테스트로 검증되는지, 구현 중 임의의 가정이 추가됐는지를 확인합니다. 비기능 요구사항도 문서에만 있고 실제 성능·보안 테스트가 없지는 않은지 살펴봐야 합니다.

결국 SDD의 핵심 디버깅 질문은 “코드가 명세를 어겼는가?”와 “명세가 현실을 잘못 표현했는가?”를 구분하는 것입니다.

| --- | --- |
| 한 줄 정의 | 명세를 기준으로 설계·작업·코드·테스트를 만들고 검증하는 개발 방식 |
| 등장 배경 | 문서와 코드의 불일치, 모호한 요구사항, AI의 임의적인 추측 |
| 핵심 원리 | 명세 우선, 검증 가능한 조건, 추적성, 반복적 개선, 사람의 승인 |

| 면접 한마디 | SDD는 문서를 많이 작성하는 절차가 아니라, 검증 가능한 명세를 구현의 기준으로 유지하는 방법이다. |
