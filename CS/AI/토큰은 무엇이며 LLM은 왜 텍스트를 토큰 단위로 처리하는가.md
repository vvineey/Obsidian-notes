# 토큰은 무엇이며 LLM은 왜 텍스트를 토큰 단위로 처리하는가?

## 질문 의도

이 질문은 LLM이 문자열을 숫자로 변환하는 입력 과정을 이해하는지 확인한다. 단순히 "토큰은 단어의 조각이다"라고 정의하는 데 그치지 않고, 왜 단어·문자 대신 서브워드를 사용하는지, 토큰의 크기와 어휘 사전이 어떻게 결정되는지, 토큰 수가 비용·속도·문맥 길이에 어떤 영향을 주는지 설명할 수 있어야 한다.

특히 한국어의 교착어적 특성, 학습 데이터 구성, Unicode와 바이트 표현이 토큰 효율에 미치는 영향도 함께 설명하는 것이 핵심이다.

## 전체 내용 정리

### 1. 토큰이란 무엇인가?

토큰은 LLM이 텍스트를 읽고 계산할 때 사용하는 기본 처리 단위다.

사람에게 입력은 문자열로 보이지만, 신경망은 문자열을 직접 계산할 수 없다. 따라서 토크나이저가 텍스트를 여러 토큰으로 나누고, 각 토큰을 어휘 사전에 등록된 정수 ID로 변환한다.

전체 흐름은 다음과 같다.

> 원문 텍스트 → 정규화와 사전 분리 → 토큰화 → 토큰 ID 변환 → 임베딩 벡터 변환 → Transformer 처리 → 다음 토큰의 확률 예측

예를 들어 `나는 학교에 간다`라는 문장은 토크나이저에 따라 다음처럼 나뉠 수 있다.

| 기준 | 분할 예시 |
| --- | --- |
| 단어 단위 | `나는` / `학교에` / `간다` |
| 형태소 단위 | `나` / `는` / `학교` / `에` / `가` / `ㄴ다` |
| 서브워드 단위 | `나는` / `학교` / `에` / `간` / `다` |
| 문자 단위 | `나` / `는` / `학` / `교` / `에` / `간` / `다` |

실제 분할 결과는 모델과 토크나이저마다 다르다. 같은 문장도 GPT 계열, BERT 계열 또는 한국어 특화 모델에서 서로 다른 토큰 수가 나올 수 있다.

토큰은 반드시 완전한 단어일 필요가 없다. 하나의 토큰은 단어 전체, 어근이나 접사, 글자, 문장 부호, 공백이 포함된 문자열 또는 바이트 조각일 수 있다.

### 2. 왜 단어 단위가 아니라 토큰 단위로 처리하는가?

핵심 이유는 제한된 크기의 어휘 사전으로 모든 언어와 새로운 표현을 처리하면서, 입력 시퀀스 길이도 적절하게 유지하기 위해서다.

#### 단어 단위 토큰화의 문제

모든 단어를 어휘 사전에 등록하면 사전이 지나치게 커진다. 한국어의 `먹다`, `먹었다`, `먹겠습니다`, `먹었었겠지만`처럼 하나의 어근에 조사와 어미가 결합하면 매우 많은 단어 형태가 만들어진다.

신조어, 오타, 사람 이름, 제품명, URL, 코드도 계속 등장한다. 학습할 때 없었던 단어는 미등록 단어인 OOV가 되어 의미를 잃을 수 있다.

#### 문자 단위 토큰화의 문제

문자 단위는 새로운 단어도 처리할 수 있고 어휘 사전도 작게 유지할 수 있다. 하지만 문장이 너무 많은 토큰으로 나뉜다.

토큰 수가 많아지면 모델이 처리해야 할 시퀀스가 길어지고, 단어보다 작은 조각에서 의미를 조합해야 한다. 결과적으로 계산량, 메모리 사용량과 학습 난도가 증가한다.

#### 서브워드 단위의 절충

현대 LLM은 주로 단어와 문자 사이 크기인 서브워드 토큰을 사용한다.

자주 등장하는 문자열은 하나의 긴 토큰으로 저장하고, 드물거나 처음 보는 단어는 여러 개의 작은 토큰으로 분해한다.

예를 들어 자주 등장하는 `computer`는 하나의 토큰이 될 수 있지만, 드문 파생어는 `compute`와 접미사 조각으로 나뉠 수 있다. 한국어도 자주 등장하는 단어나 어절은 크게 묶이고, 드문 활용형은 어근·조사·어미 또는 더 작은 문자 조각으로 분해될 수 있다.

서브워드 방식은 다음 두 목표 사이에서 균형을 잡는다.

- 어휘 사전을 무한히 키우지 않는다.
- 문자 단위처럼 시퀀스가 지나치게 길어지는 것을 막는다.

### 3. 토큰의 크기를 정하는 기준은 무엇인가?

토큰의 크기는 사람이 "한 토큰은 몇 글자"처럼 고정해서 정하지 않는다. 토크나이저가 학습 말뭉치의 문자열 빈도와 선택한 알고리즘, 목표 어휘 크기를 바탕으로 결정한다.

여기서 토큰의 크기는 두 의미로 구분해야 한다.

- **개별 토큰의 길이:** 하나의 토큰에 몇 글자나 바이트가 포함되는가
- **어휘 사전의 크기:** 모델이 구분할 수 있는 토큰 종류가 총 몇 개인가

주요 결정 기준은 다음과 같다.

#### 학습 말뭉치

어떤 언어와 도메인의 텍스트가 얼마나 포함됐는지가 가장 중요하다. 자주 등장하는 문자열은 하나의 토큰으로 합쳐질 가능성이 높다.

영어 데이터가 많은 말뭉치에서 학습한 토크나이저는 영어 단어를 긴 토큰 하나로 표현할 가능성이 크다. 한국어 데이터가 상대적으로 적으면 한국어 표현이 더 작은 조각으로 나뉠 수 있다.

#### 어휘 사전 크기

어휘 사전이 크면 더 많은 단어와 긴 문자열을 하나의 토큰으로 저장할 수 있어 시퀀스가 짧아진다.

하지만 토큰 임베딩과 출력 확률을 계산하는 계층의 파라미터와 메모리 비용이 커진다. 반대로 어휘 사전이 작으면 모델 크기는 줄일 수 있지만 같은 문장이 더 많은 토큰으로 분할될 수 있다.

#### 빈도와 압축 효율

자주 반복되는 문자열을 하나로 합치면 말뭉치 전체를 더 적은 토큰으로 표현할 수 있다. BPE 계열은 이런 빈도 기반 병합을 대표적으로 사용한다.

#### 언어적 특성

띄어쓰기, 접사, 굴절, 조사와 어미, 합성어의 생성 방식에 따라 효율적인 토큰 경계가 달라진다.

#### 전처리와 정규화

대소문자 변환, Unicode 정규화, 공백 처리, 악센트 제거 여부도 토큰 경계에 영향을 준다. 겉으로 같은 글자처럼 보여도 내부 Unicode 표현이 다르면 서로 다른 조각으로 처리될 수 있다.

#### 토크나이저 알고리즘

BPE는 자주 함께 등장하는 조각을 반복해서 합치고, WordPiece는 어휘에 추가했을 때 말뭉치를 얼마나 잘 설명하는지 고려한다. Unigram 방식은 큰 후보 어휘에서 시작해 중요도가 낮은 토큰을 제거한다.

### 4. 대표적인 토큰화 방식

#### 단어 단위 토큰화

공백이나 구두점을 기준으로 단어를 나눈다.

장점은 결과가 사람이 이해하기 쉽고 시퀀스가 비교적 짧다는 것이다. 하지만 어휘 사전이 매우 커지고, 신조어와 활용형 같은 미등록 단어에 약하다. 띄어쓰기가 불규칙하거나 단어 형태가 다양하게 변하는 언어에도 불리하다.

#### 문자 단위 토큰화

각 문자를 하나의 토큰으로 사용한다.

어휘 사전이 작고 처음 보는 단어도 표현할 수 있다는 장점이 있다. 반면 입력 시퀀스가 길어지고, 모델이 여러 글자를 조합해 단어의 의미를 학습해야 한다.

#### 형태소 단위 토큰화

문장을 어근, 조사, 어미 같은 의미·문법 단위로 나눈다.

한국어의 구조를 잘 반영할 수 있지만 형태소 분석기의 정확도와 언어별 규칙에 의존한다. 신조어, 오타, 고유명사, 코드가 섞인 범용 LLM 입력을 일관되게 처리하기 어렵고 모든 언어에 같은 방식을 적용하기도 어렵다.

#### BPE

Byte Pair Encoding은 처음에 문자나 바이트 같은 작은 단위에서 시작한 뒤, 말뭉치에서 자주 인접하는 두 조각을 반복해서 합친다.

예를 들어 `low`, `lower`, `lowest`가 자주 등장한다면 공통 문자열인 `low`가 하나의 토큰으로 만들어질 수 있다.

구현이 단순하고 자주 나오는 표현을 짧게 인코딩할 수 있다. 다만 빈도를 중심으로 병합하기 때문에 언어학적으로 자연스러운 형태소 경계를 항상 보장하지는 않는다.

#### Byte-level BPE

텍스트를 Unicode 문자보다 더 아래 단계인 UTF-8 바이트로 표현한 뒤 BPE 병합을 적용한다.

모든 텍스트를 바이트 조합으로 표현할 수 있어 미등록 문자를 거의 없앨 수 있다. 이모지, 특수문자, 여러 언어가 섞인 입력도 처리할 수 있다.

하지만 자주 학습되지 않은 비라틴 문자는 여러 바이트 또는 작은 조각으로 분해될 수 있다. 그 결과 한국어처럼 UTF-8에서 한 글자가 여러 바이트로 표현되는 문자는 토큰 효율이 낮아질 수 있다.

#### WordPiece

WordPiece는 BERT 계열 모델에서 널리 알려진 서브워드 방식이다. 단순히 가장 자주 등장하는 쌍만 합치는 것이 아니라, 어떤 조각을 어휘에 포함했을 때 학습 데이터를 효율적으로 설명할 수 있는지를 고려한다.

자주 쓰이는 단어는 하나의 토큰이 되고 드문 단어는 여러 서브워드로 나뉜다. 구현에 따라 단어 내부의 후속 조각임을 나타내는 접두 표기를 사용하기도 한다.

#### Unigram Language Model

큰 토큰 후보 집합에서 시작한 뒤, 말뭉치를 설명하는 데 덜 중요한 토큰을 반복해서 제거한다.

한 문자열을 나누는 후보가 여러 개일 수 있으며, 각 후보의 확률을 기준으로 적절한 분할을 선택한다. SentencePiece에서 사용할 수 있는 대표 알고리즘 중 하나다.

#### SentencePiece

SentencePiece는 특정 토큰화 알고리즘 하나라기보다, 원문에서 직접 서브워드 모델을 학습하고 적용할 수 있는 도구와 처리 방식에 가깝다.

공백도 일반 기호처럼 다룰 수 있어 언어별 공백 규칙에 덜 의존한다. 내부 알고리즘으로 BPE나 Unigram을 사용할 수 있다. 따라서 "SentencePiece와 BPE"를 완전히 동등한 경쟁 알고리즘으로 비교하면 부정확하다.

### 5. 토큰화 예시

`인공지능을 공부합니다`라는 문장을 생각해 보자.

토크나이저 A는 한국어 데이터가 충분해 다음과 같이 처리할 수 있다.

> `인공지능` / `을` / `공부` / `합니다`

반면 한국어 표현이 어휘에 충분히 학습되지 않은 토크나이저 B는 다음과 같이 더 잘게 나눌 수 있다.

> `인` / `공지` / `능` / `을` / `공` / `부` / `합` / `니다`

바이트 기반 토크나이저에서는 일부 드문 문자가 바이트 조각에 가까운 단위로 더 분해될 수도 있다.

A에서는 4개의 토큰이지만 B에서는 8개 이상의 토큰이 될 수 있다. 같은 컨텍스트 창을 사용해도 B가 실제로 담을 수 있는 한국어 정보량은 더 적다.

이 예시는 원리를 설명하기 위한 것이며, 실제 분할과 토큰 수는 반드시 해당 모델의 토크나이저로 측정해야 한다.

### 6. 토큰 수가 많아지면 어떤 문제가 발생하는가?

#### 컨텍스트 창을 더 빨리 소모한다

LLM의 입력 한도는 보통 글자 수나 단어 수가 아니라 토큰 수를 기준으로 한다.

같은 내용을 표현하더라도 토큰화 효율이 낮으면 문서, 대화 기록, 검색 결과를 더 적게 넣을 수 있다. 한도를 넘으면 앞부분을 제거하거나 문서를 잘라야 하므로 중요한 정보가 손실될 수 있다.

#### 비용이 증가한다

많은 LLM API는 입력 토큰과 출력 토큰 수를 기준으로 사용량을 계산한다. 같은 의미의 문장이어도 더 많은 토큰으로 분할되는 언어는 더 많은 비용이 들 수 있다.

다만 실제 과금 방식과 캐시 할인 여부는 서비스마다 다르므로 사용하는 API의 정책을 확인해야 한다.

#### 응답 시간이 증가한다

입력 토큰이 많으면 모델이 처리해야 할 시퀀스가 길어진다. 프롬프트를 처음 읽고 내부 상태를 만드는 prefill 단계의 시간이 증가하고, 출력 토큰이 많으면 한 토큰씩 생성하는 decoding 시간도 늘어난다.

#### 메모리 사용량이 증가한다

시퀀스가 길어질수록 중간 활성값과 attention 계산에 필요한 메모리가 증가한다. 추론 중에는 이전 토큰의 key와 value를 저장하는 KV cache도 토큰 수에 비례해 커진다.

#### 계산량이 증가한다

전통적인 self-attention은 시퀀스 길이 `n`에 대해 attention score 계산량과 메모리가 대체로 `n²`에 비례한다. 따라서 토큰 수가 두 배가 되면 attention 부분의 부담은 단순히 두 배가 아니라 더 크게 늘어날 수 있다.

최근에는 효율적인 attention 구현과 다양한 최적화가 사용되지만, 토큰 수 증가가 계산 비용과 메모리 부담을 높인다는 기본 방향은 같다.

#### 정보 손실 위험이 증가한다

컨텍스트 제한 때문에 문서를 잘라내거나 요약해야 할 수 있다. RAG에서는 검색된 문서 조각이 너무 많은 토큰을 차지하면 중요한 근거가 제외되거나, 관련 없는 문서가 컨텍스트를 채울 수 있다.

#### 출력 가능한 분량이 줄어든다

일부 모델이나 API는 입력과 출력이 하나의 전체 토큰 한도를 공유한다. 입력이 길어지면 답변에 사용할 수 있는 출력 토큰 예산이 줄어들 수 있다.

#### 언어 이해 난도가 높아질 수 있다

하나의 의미 단위가 지나치게 많은 조각으로 분해되면 모델은 여러 토큰을 조합해서 원래 단어의 의미와 문법적 관계를 복원해야 한다.

토큰화가 잘게 된다고 반드시 이해도가 낮아지는 것은 아니지만, 같은 모델 용량과 학습량이라면 비효율적인 분할은 학습과 추론에 불필요한 부담을 줄 수 있다.

### 7. 한국어는 왜 더 불리할 수 있는가?

#### 교착어이기 때문이다

한국어는 어근에 조사와 어미가 결합해 문법적 의미를 표현하는 교착어다.

`먹다`라는 기본형에서 `먹었다`, `먹었지만`, `먹겠습니다`, `먹었었겠지만`처럼 많은 표면 형태가 만들어진다. 단어 단위 어휘 사전으로 이들을 모두 저장하기 어렵기 때문에 여러 서브워드로 나뉘기 쉽다.

#### 어절 하나에 여러 정보가 들어간다

영어에서는 전치사나 조동사처럼 분리된 단어로 표현되는 정보가 한국어에서는 조사나 어미로 붙는다.

`학교에서도`는 `학교 + 에서 + 도`라는 여러 의미를 한 어절 안에 포함한다. 토크나이저가 이런 결합을 충분히 학습하지 못했다면 어절을 여러 토큰으로 분리하게 된다.

#### 띄어쓰기 변형이 많다

한국어는 띄어쓰기에 따라 동일하거나 유사한 표현이 여러 문자열 형태로 나타날 수 있다. 사용자 입력에서는 띄어쓰기 오류도 자주 발생한다.

토크나이저가 공백을 토큰 경계나 토큰의 일부로 활용하면 `할 수 있다`와 `할수있다`가 서로 다른 방식으로 분할될 수 있다.

#### 다국어 학습 데이터의 비율이 다를 수 있다

토크나이저는 자주 등장하는 문자열에 어휘 공간을 더 많이 배정한다.

영어 중심의 말뭉치로 학습했다면 제한된 어휘 사전의 상당 부분이 영어 단어와 영어에서 자주 등장하는 조각에 할당될 수 있다. 상대적으로 적게 등장한 한국어 문자열은 긴 토큰으로 병합될 기회가 적어 더 잘게 나뉜다.

#### UTF-8 바이트 표현의 영향이 있다

영문 알파벳은 UTF-8에서 보통 문자 하나가 1바이트지만, 완성형 한글 음절은 일반적으로 3바이트로 표현된다.

바이트 기반 토크나이저가 충분히 자주 등장한 한글 바이트 조합을 하나의 토큰으로 병합했다면 문제가 완화된다. 그러나 드문 한글 표현이나 학습이 부족한 문자열은 여러 바이트 조각으로 남아 영어보다 많은 토큰이 될 수 있다.

#### Unicode 표현 차이가 영향을 줄 수 있다

한글은 완성형 음절과 자모 조합 등 서로 다른 Unicode 표현이 가능하다. 화면에는 비슷하게 보여도 내부 코드 포인트 배열이 다를 수 있다.

정규화가 일관되지 않으면 동일하게 보이는 문자열이 서로 다르게 토큰화될 수 있다. 일반적인 자연어 문장뿐 아니라 옛한글, 분리된 자모, 비정상적으로 복사된 텍스트에서 특히 문제가 될 수 있다.

#### 다만 한국어가 항상 불리한 것은 아니다

"한국어는 영어보다 무조건 몇 배 많은 토큰을 사용한다"라고 일반화하면 안 된다.

한국어 데이터로 충분히 학습한 토크나이저나 한국어 특화 모델은 자주 등장하는 어절과 형태소를 효율적으로 하나의 토큰으로 처리할 수 있다. 모델마다 어휘 사전, 학습 데이터와 정규화 방식이 다르므로 실제 차이는 해당 토크나이저로 측정해야 한다.

정확한 결론은 "한국어의 언어 구조 자체와 영어 중심 학습 데이터, 바이트 표현이 결합하면 토큰 수가 많아질 가능성이 있다"이다.

### 8. 장단점과 트레이드오프

| 방식 또는 선택 | 장점 | 단점 / 주의점 |
| --- | --- | --- |
| 단어 단위 | 시퀀스가 짧고 사람이 이해하기 쉽다. | 어휘 사전이 커지고 신조어·활용형·오타에 약하다. |
| 문자 또는 바이트 단위 | 거의 모든 입력을 표현할 수 있고 OOV 문제를 줄인다. | 시퀀스가 길어져 계산량과 문맥 사용량이 증가한다. |
| 서브워드 단위 | 열린 어휘를 지원하면서 시퀀스 길이와 어휘 사전 크기의 균형을 잡는다. | 분할 결과가 언어학적으로 자연스럽지 않을 수 있고 언어별 토큰 효율 격차가 발생할 수 있다. |
| 큰 어휘 사전 | 자주 쓰는 단어를 하나의 토큰으로 표현해 시퀀스를 줄일 수 있다. | 임베딩과 출력 계층이 커지고 드물게 쓰이는 토큰은 충분히 학습되지 않을 수 있다. |
| 작은 어휘 사전 | 모델의 어휘 관련 파라미터를 줄이고 각 토큰의 학습 빈도를 높일 수 있다. | 문장이 더 많은 토큰으로 나뉘어 Transformer 계산과 컨텍스트 사용량이 증가한다. |

### 9. 헷갈리기 쉬운 지점

- 토큰 하나가 항상 단어 하나인 것은 아니다.
- 토큰 하나가 항상 일정한 글자 수를 갖는 것도 아니다.
- 공백과 문장 부호도 독립 토큰이 되거나 다른 문자열과 묶일 수 있다.
- 토큰화는 형태소 분석과 같지 않다. 형태소 분석은 언어학적 의미와 문법 구조를 찾지만, 일반적인 서브워드 토큰화는 주로 말뭉치 통계와 압축 효율을 이용한다.
- Tokenization과 Embedding은 다른 단계다. 토큰화는 문자열을 토큰 ID로 바꾸고, 임베딩은 그 ID를 연속적인 숫자 벡터로 변환한다.
- BPE와 Byte-level BPE는 동일하지 않다. BPE는 병합 알고리즘이고, Byte-level BPE는 시작 단위로 바이트를 사용하는 BPE 계열 방식이다.
- SentencePiece는 하나의 고정된 분할 알고리즘이 아니다. BPE나 Unigram 같은 알고리즘을 적용할 수 있는 도구이자 처리 체계다.
- 토큰 수만으로 모델의 언어 능력을 단정할 수는 없다. 학습 데이터, 모델 크기, 문맥 구성, 아키텍처와 평가 과제가 함께 영향을 준다.
- 자연어의 단어 수와 API에서 계산되는 토큰 수는 다르므로 비용을 추정할 때 단어 수만 세면 안 된다.

### 10. 실무 연결

#### 프롬프트와 RAG 설계

RAG에서는 문서를 글자 수가 아니라 최종 모델의 토큰 수를 기준으로 잘라야 한다. 임베딩 모델의 토크나이저와 생성 LLM의 토크나이저가 다를 수도 있으므로 두 모델의 한도를 각각 확인해야 한다.

Chunk를 너무 작게 만들면 문맥이 끊기고 검색 결과 수가 늘어난다. 너무 크게 만들면 하나의 chunk가 많은 토큰을 차지하고 검색 정확도가 떨어질 수 있다.

#### API 비용 추정

서비스가 다국어를 지원한다면 영어 샘플만으로 비용을 계산하면 안 된다. 실제 한국어 사용자 입력, 시스템 프롬프트, 대화 기록, 검색 문서를 모델의 공식 토크나이저로 측정해야 한다.

#### 컨텍스트 관리

다음 항목별 토큰 사용량을 분리해 관찰하는 것이 좋다.

- 시스템 프롬프트
- 사용자 질문
- 이전 대화 기록
- 도구 호출 결과
- RAG 검색 문서
- 모델 출력

한도를 넘을 때는 무조건 앞부분을 자르기보다 오래된 대화를 요약하고, 중복 검색 문서를 제거하며, 관련도가 낮은 chunk를 제외해야 한다.

#### 모델 변경

모델을 교체하면 토크나이저와 컨텍스트 한도도 달라질 수 있다. 같은 프롬프트의 토큰 수, 비용, 지연 시간과 최대 입력 가능 문서량을 다시 측정해야 한다.

#### 사용자 입력 검증

보이지 않는 Unicode 문자, 비정상적으로 반복된 문자, 분리된 자모는 예상보다 많은 토큰을 만들 수 있다. 입력 글자 수만 제한하면 토큰 수 공격이나 과도한 비용을 막지 못할 수 있으므로 서버에서도 토큰 수 또는 실제 요청 크기를 검증해야 한다.

#### 운영 지표

- 요청별 입력 토큰 수
- 요청별 출력 토큰 수
- 언어별 평균 토큰 수
- 글자 수 대비 토큰 수
- RAG 문서가 차지하는 토큰 비율
- 최대 컨텍스트 초과율
- 입력 길이별 응답 지연 시간
- 입력 및 출력 토큰 비용

## 꼬리 질문과 답변

### 1. 토큰이란 무엇이며 LLM은 왜 단어 대신 토큰 단위로 처리하나요?

**답변**

토큰은 LLM이 텍스트를 숫자로 바꾸어 계산할 때 사용하는 기본 단위입니다. 단어 단위로 처리하면 활용형, 신조어와 고유명사를 모두 어휘 사전에 넣어야 하므로 사전이 지나치게 커지고 미등록 단어 문제가 생깁니다. 반대로 문자 단위는 모든 입력을 표현할 수 있지만 시퀀스가 너무 길어집니다. 그래서 현대 LLM은 자주 쓰는 표현은 크게 묶고 드문 표현은 작게 나누는 서브워드 토큰을 주로 사용해 어휘 크기와 시퀀스 길이 사이의 균형을 잡습니다.

### 2. 토큰 하나의 크기는 어떻게 정해지나요?

**답변**

토큰의 길이는 고정된 글자 수로 정하지 않습니다. 토크나이저가 학습 말뭉치에서 문자열이 등장하는 빈도, 목표 어휘 사전 크기, 정규화 방식과 BPE·WordPiece·Unigram 같은 학습 알고리즘을 바탕으로 결정합니다. 자주 등장하는 문자열은 하나의 긴 토큰이 되기 쉽고, 드문 문자열은 여러 작은 조각으로 분해됩니다. 따라서 동일한 문장도 모델의 학습 데이터와 토크나이저에 따라 토큰 수가 달라집니다.

### 3. 대표적인 토큰화 방식에는 무엇이 있나요?

**답변**

큰 범주로는 단어, 문자, 형태소와 서브워드 단위가 있습니다. 현대 LLM에서는 서브워드 방식이 주로 사용됩니다. BPE는 자주 인접하는 조각을 반복해서 합치고, WordPiece는 말뭉치를 더 잘 설명하는 조각을 선택하며, Unigram은 큰 후보 어휘에서 중요도가 낮은 토큰을 제거합니다. Byte-level BPE는 바이트에서 시작해 모든 Unicode 입력을 표현할 수 있다는 장점이 있습니다. SentencePiece는 BPE나 Unigram을 원문에 적용할 수 있는 도구이므로 독립적인 단일 알고리즘으로만 보면 안 됩니다.

### 4. 토큰 수가 많아지면 실제로 어떤 문제가 발생하나요?

**답변**

토큰 수가 많으면 컨텍스트 창을 빨리 소모하고 API 비용, 응답 시간과 메모리 사용량이 증가합니다. 긴 입력은 더 많은 attention 계산을 요구하고, 추론 중에는 KV cache도 커집니다. 컨텍스트 한도를 초과하면 대화나 문서를 잘라야 하므로 중요한 정보가 사라질 수도 있습니다. 특히 RAG에서는 검색 문서가 많은 토큰을 차지하면 실제 답변에 필요한 근거와 출력 공간이 줄어들기 때문에 토큰 기준의 chunking과 문서 선택이 중요합니다.

### 5. 한국어는 왜 토큰 수 문제에서 불리한가요?

**답변**

한국어는 어근에 조사와 어미가 결합해 많은 표현을 만드는 교착어이므로 하나의 어절이 여러 서브워드로 나뉘기 쉽습니다. 또한 영어 중심의 말뭉치로 토크나이저가 학습됐다면 한국어 문자열이 긴 토큰으로 등록될 기회가 적습니다. Byte-level 토크나이저에서는 UTF-8 한글 음절이 여러 바이트로 표현된다는 점도 토큰 수를 늘릴 수 있습니다. 다만 한국어 특화 토크나이저는 이런 문제를 완화할 수 있으므로, 한국어가 항상 몇 배 불리하다고 단정하지 말고 실제 모델의 토크나이저로 측정해야 합니다.

### 6. 토큰 수를 줄이기 위해 어휘 사전을 무조건 크게 만들면 되나요?

**답변**

그렇지 않습니다. 어휘 사전을 키우면 긴 단어나 자주 쓰는 표현을 하나의 토큰으로 처리할 수 있어 시퀀스는 짧아집니다. 하지만 토큰 임베딩과 출력 계층의 파라미터와 메모리가 커지고, 드문 토큰은 학습 예제가 부족해 표현 품질이 낮을 수 있습니다. 반대로 사전이 너무 작으면 어휘 관련 파라미터는 줄지만 입력이 잘게 분할됩니다. 따라서 언어 범위, 모델 크기, 학습 데이터와 목표 시퀀스 길이를 함께 고려해야 합니다.

### 7. 서비스에서 한국어의 토큰 비용 문제를 어떻게 관리하겠습니까?

**답변**

먼저 실제 서비스 문장을 대상 모델의 토크나이저로 측정해 언어별 글자 수 대비 토큰 수와 요청별 비용을 확인하겠습니다. 이후 반복되는 시스템 프롬프트를 줄이고, 대화 기록을 요약하며, RAG 문서는 토큰 기준으로 나누고 중복 chunk를 제거하겠습니다. 또한 모델을 변경할 때 토큰 수와 품질을 다시 비교하고, 요청별 입력·출력 토큰, 컨텍스트 초과율과 응답 지연 시간을 모니터링하겠습니다. 단순히 한국어 문장을 임의로 축약하면 의미와 품질이 손상될 수 있으므로 비용과 답변 품질을 함께 평가해야 합니다.

## 마지막 요약

| 구분 | 핵심 내용 |
| --- | --- |
| 한 문장 정의 | 토큰은 LLM이 텍스트를 숫자로 변환해 처리하고 예측하는 기본 단위다. |
| 필요한 이유 | 단어 단위의 거대한 어휘와 OOV 문제, 문자 단위의 긴 시퀀스 문제 사이에서 균형을 잡기 위해 필요하다. |
| 핵심 원리 | 토크나이저가 학습 말뭉치의 빈도, 목표 어휘 크기와 알고리즘을 바탕으로 자주 쓰는 문자열은 크게 묶고 드문 문자열은 작게 나눈다. |
| 대표 방식 | 단어, 문자, 형태소, BPE, Byte-level BPE, WordPiece, Unigram 방식이 있다. |
| 토큰 증가의 문제 | 컨텍스트 소모, 비용, 지연 시간, attention 계산량, KV cache와 메모리 사용량이 증가하고 정보가 잘릴 가능성이 커진다. |
| 한국어가 불리한 이유 | 교착어적 구조, 띄어쓰기 변형, 영어 중심 학습 데이터, UTF-8 바이트 표현 때문에 더 작은 조각으로 분할될 수 있다. |
| 주의할 점 | 한국어가 항상 더 많은 토큰을 사용한다고 단정할 수는 없다. 실제 결과는 모델과 토크나이저별로 측정해야 한다. |
| 면접 한마디 | 서브워드 토큰화는 열린 어휘를 지원하면서 어휘 사전 크기와 시퀀스 길이를 절충하는 방식이며, 한국어에서는 언어 구조와 학습 데이터 구성 때문에 토큰 효율이 낮아질 수 있다. |
