# RAG는 무엇이고 왜 파인튜닝만으로는 부족한가?

## 질문 의도

이 질문은 LLM 애플리케이션에서 외부 지식을 어떻게 연결하는지 이해하는지 확인한다. 단순히 "문서를 검색해서 프롬프트에 넣는 기술"이라고 외우는 것이 아니라, 파인튜닝과 RAG의 역할 차이, 검색-증강-생성 파이프라인, 벡터 검색 품질 개선 방법, 그리고 실무 운영에서 생기는 문제까지 설명할 수 있어야 한다.

## 전체 내용 정리

### 1. 개념

RAG, Retrieval-Augmented Generation은 LLM이 답변을 생성하기 전에 외부 지식 저장소에서 관련 문서를 검색하고, 그 검색 결과를 프롬프트 컨텍스트에 넣어 답변을 생성하게 하는 방식이다.

쉽게 말하면 RAG는 "모델의 기억만 믿지 않고, 답변 직전에 필요한 자료를 찾아서 근거로 쓰게 하는 구조"다. 예를 들어 사내 위키, API 문서, 상품 정책, 장애 로그, 법무 문서처럼 계속 바뀌는 정보를 LLM이 직접 외우게 하는 대신, 검색 시스템을 통해 최신 문서를 가져와 답변하게 한다.

RAG는 보통 다음 문제를 줄이기 위해 사용한다.

| 문제 | RAG가 해결하는 방식 |
| --- | --- |
| 모델 지식이 오래됨 | 최신 문서를 검색해 컨텍스트로 제공 |
| 환각(hallucination) | 근거 문서 기반으로 답변하도록 유도 |
| 사내/비공개 데이터 부족 | 내부 문서를 인덱싱해 검색 가능하게 함 |
| 파인튜닝 비용/주기 부담 | 데이터 변경 시 모델 재학습 대신 인덱스 갱신 |
| 답변 근거 부족 | 문서 출처, 조각, 링크를 함께 제공 가능 |

### 2. 등장 배경 / 필요한 이유

LLM은 학습 시점의 일반 지식을 잘 다루지만, 모든 최신 정보와 조직 내부 정보를 알고 있지는 않다. 또한 모델 파라미터 안에 지식을 넣어두면 언제, 어떤 근거로 답했는지 추적하기 어렵다.

파인튜닝은 모델의 말투, 출력 형식, 특정 작업 패턴, 도메인 적응에는 유용하다. 하지만 자주 바뀌는 사실 정보나 대량의 사내 문서를 계속 반영하는 데는 부담이 크다. 데이터가 바뀔 때마다 학습 데이터를 준비하고, 학습하고, 평가하고, 배포해야 하기 때문이다.

그래서 실무에서는 보통 다음처럼 역할을 나눈다.

| 방식 | 잘하는 것 | 부족한 점 |
| --- | --- | --- |
| Prompting | 빠른 지시, 형식 제어 | 긴 지식 저장에는 부적합 |
| Fine-tuning | 말투, 정책, 태스크 수행 패턴 학습 | 최신 사실 반영과 근거 추적이 어려움 |
| RAG | 외부 지식 검색, 최신성, 출처 제공 | 검색 품질과 컨텍스트 구성에 성능이 크게 좌우됨 |

즉, 파인튜닝은 "모델이 어떻게 답할지"를 개선하는 데 가깝고, RAG는 "무엇을 근거로 답할지"를 제공하는 데 가깝다.

### 3. 동작 원리

RAG의 핵심 파이프라인은 크게 3단계로 볼 수 있다.

1. Indexing
2. Retrieval
3. Generation

#### 1단계: Indexing

문서를 수집하고 검색 가능한 형태로 저장하는 단계다.

일반적인 흐름은 다음과 같다.

1. 원본 문서를 수집한다.
2. HTML, PDF, Markdown, DB row 같은 데이터를 텍스트로 정제한다.
3. 긴 문서를 chunk 단위로 나눈다.
4. 각 chunk를 embedding model로 vector로 변환한다.
5. vector, 원문, metadata, 출처 정보를 Vector DB나 검색 엔진에 저장한다.

이 단계에서 자주 생기는 문제는 다음과 같다.

| 문제 | 설명 |
| --- | --- |
| Chunking 실패 | 너무 작으면 맥락이 끊기고, 너무 크면 검색 정확도와 토큰 효율이 떨어짐 |
| 문서 정제 실패 | 메뉴, footer, 중복 문구, 깨진 텍스트가 검색 결과를 오염시킴 |
| Metadata 부족 | 권한, 문서 버전, 작성일, 서비스명으로 필터링하기 어려움 |
| 인덱스 최신성 문제 | 문서가 바뀌었는데 vector index가 갱신되지 않아 오래된 답을 함 |
| 임베딩 모델 불일치 | query와 document 임베딩 방식이 맞지 않으면 유사도 검색 품질이 떨어짐 |

#### 2단계: Retrieval

사용자 질문과 관련 있는 문서 조각을 찾는 단계다.

일반적인 흐름은 다음과 같다.

1. 사용자 질문을 정제하거나 재작성한다.
2. 질문을 embedding vector로 변환한다.
3. Vector DB에서 유사한 chunk를 top-k로 검색한다.
4. metadata filter나 keyword search를 함께 적용한다.
5. reranker로 후보 문서의 순서를 다시 매긴다.
6. 너무 중복되거나 관련 없는 chunk를 제거한다.

이 단계에서 자주 생기는 문제는 다음과 같다.

| 문제 | 설명 |
| --- | --- |
| Query ambiguity | 질문이 짧거나 모호해서 엉뚱한 문서가 검색됨 |
| Semantic mismatch | 의미는 비슷하지만 실제 답과 관련 없는 문서가 높은 점수를 받음 |
| Recall 부족 | 필요한 문서가 top-k 안에 들어오지 않음 |
| Precision 부족 | 검색 결과는 많지만 잡음이 많아 생성 품질이 떨어짐 |
| 권한 필터 누락 | 사용자가 볼 수 없는 문서가 컨텍스트로 들어갈 수 있음 |

#### 3단계: Generation

검색된 문서를 프롬프트에 넣고 LLM이 답변을 생성하는 단계다.

일반적인 흐름은 다음과 같다.

1. 검색 결과를 정렬하고 필요한 부분만 추린다.
2. 시스템 프롬프트에 답변 규칙을 넣는다.
3. 문서 조각과 출처를 컨텍스트로 넣는다.
4. 모델이 근거 기반 답변을 생성한다.
5. 필요하면 출처 표시, 후처리, 검증을 수행한다.

이 단계에서 자주 생기는 문제는 다음과 같다.

| 문제 | 설명 |
| --- | --- |
| Context overflow | 검색 결과가 너무 많아 중요한 근거가 잘리거나 비용이 증가함 |
| Lost in the middle | 긴 컨텍스트 중간의 중요한 정보가 모델에게 덜 반영됨 |
| Prompt injection | 외부 문서 안의 악성 지시를 모델이 따를 수 있음 |
| 근거 없는 답변 | 검색 결과에 답이 없는데 모델이 아는 척 답할 수 있음 |
| 출처 왜곡 | 답변 내용과 실제 근거 문서가 맞지 않을 수 있음 |

### 4. 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| Document loader | 원본 문서를 가져온다. 예: Markdown, PDF, 웹페이지, DB |
| Text splitter | 문서를 검색하기 좋은 chunk로 나눈다 |
| Embedding model | 텍스트를 의미 벡터로 변환한다 |
| Vector DB | 벡터와 원문, metadata를 저장하고 유사도 검색을 수행한다 |
| Retriever | 질문에 맞는 후보 문서를 가져온다 |
| Reranker | 후보 문서의 관련도를 다시 평가해 순서를 개선한다 |
| Prompt builder | 검색 결과를 모델 입력 컨텍스트로 구성한다 |
| Generator | LLM이 최종 답변을 생성한다 |
| Evaluator | 검색 품질과 답변 품질을 평가한다 |

### 5. 예시

사내 장애 대응 챗봇을 만든다고 가정하자.

1. 장애 대응 매뉴얼, Runbook, Postmortem 문서를 수집한다.
2. 문서를 서비스명, 장애 유형, 작성일, 권한 정보와 함께 chunk로 나눈다.
3. 각 chunk를 embedding해서 Vector DB에 저장한다.
4. 사용자가 "결제 API timeout이 늘어났을 때 확인할 것"을 질문한다.
5. 시스템은 `payment`, `timeout`, `runbook` 관련 문서를 검색한다.
6. 검색 결과를 reranking해서 가장 관련 높은 절차를 컨텍스트로 넣는다.
7. LLM은 "먼저 gateway latency, DB connection pool, 외부 PG 응답 시간을 확인하라"처럼 문서 기반 답변을 생성한다.
8. 답변 아래에 참고한 문서 링크를 붙인다.

이때 RAG가 없으면 모델은 일반적인 장애 대응 방법을 말할 수는 있지만, 회사 내부의 실제 대시보드 이름, 알람 규칙, 담당 팀, 운영 절차는 알기 어렵다.

### 6. 장단점 / 트레이드오프

| 관점 | 장점 | 단점 / 주의점 |
| --- | --- | --- |
| 최신성 | 문서 인덱스만 갱신하면 최신 정보 반영 가능 | 인덱스 갱신 파이프라인이 깨지면 오래된 답변을 할 수 있음 |
| 비용 | 모델 재학습보다 빠르고 저렴하게 지식 반영 가능 | 검색 인프라, 임베딩 비용, 저장소 비용이 추가됨 |
| 정확성 | 근거 문서를 넣어 환각을 줄일 수 있음 | 잘못 검색하면 그럴듯한 오답이 더 강해질 수 있음 |
| 추적성 | 출처를 함께 제공할 수 있음 | 출처와 답변 내용이 실제로 일치하는지 검증 필요 |
| 보안 | 권한 기반 검색을 붙일 수 있음 | 필터 누락 시 민감 문서 유출 위험 |
| 운영 | 문서 추가/삭제로 지식을 관리 가능 | 문서 품질, chunk 전략, 평가셋 관리가 중요함 |

### 7. 벡터DB 검색 품질을 높이는 방법

벡터DB 검색 품질은 단순히 좋은 DB를 쓰는 것보다 데이터 준비, 검색 전략, 평가 체계를 함께 개선해야 좋아진다.

| 방법 | 설명 |
| --- | --- |
| Chunk size 조정 | 문서 구조에 맞게 chunk 크기와 overlap을 조절한다 |
| 구조 기반 chunking | 제목, 섹션, 표, 코드 블록 단위로 의미가 끊기지 않게 나눈다 |
| Metadata 강화 | 서비스명, 버전, 날짜, 권한, 문서 타입 등을 저장해 필터링한다 |
| Hybrid search | vector search와 BM25/keyword search를 결합해 의미 검색과 정확한 용어 검색을 모두 챙긴다 |
| Query rewriting | 짧거나 모호한 사용자 질문을 검색에 적합하게 재작성한다 |
| Multi-query retrieval | 여러 관점의 query를 만들어 recall을 높인다 |
| Reranking | top-k 후보를 cross-encoder나 LLM reranker로 재정렬한다 |
| Deduplication | 중복 chunk를 제거해 컨텍스트 낭비를 줄인다 |
| Domain-specific embedding | 도메인 용어가 중요한 경우 적합한 embedding model을 선택하거나 학습한다 |
| Evaluation set 관리 | 실제 질문-정답-근거 문서 쌍으로 검색 품질을 지속 측정한다 |

검색 품질을 평가할 때는 다음 지표를 볼 수 있다.

| 지표 | 의미 |
| --- | --- |
| Recall@k | 정답 근거 문서가 top-k 안에 들어왔는가 |
| Precision@k | top-k 검색 결과 중 실제 관련 문서 비율 |
| MRR | 첫 번째 관련 문서가 얼마나 높은 순위에 있는가 |
| nDCG | 관련도 높은 문서가 상위에 잘 배치되었는가 |
| Answer faithfulness | 생성 답변이 검색 근거에 충실한가 |

### 8. 헷갈리기 쉬운 지점

- RAG는 파인튜닝의 완전한 대체재가 아니다. 둘은 역할이 다르다.
- Vector DB만 붙이면 RAG가 완성되는 것이 아니다. 문서 정제, chunking, metadata, retriever, prompt 구성이 모두 중요하다.
- RAG를 쓰면 환각이 사라지는 것이 아니다. 검색 결과가 틀리거나 부족하면 모델은 여전히 그럴듯한 오답을 만들 수 있다.
- top-k를 무조건 크게 하면 좋은 것이 아니다. 관련 없는 문서가 늘고 비용도 증가한다.
- 임베딩 유사도가 높다고 항상 답변 근거로 좋은 문서인 것은 아니다.
- RAG는 권한 관리가 핵심이다. 검색 단계에서 사용자별 접근 권한을 반드시 반영해야 한다.

### 9. 실무 연결

RAG 시스템은 모델보다 데이터 파이프라인에서 문제가 많이 난다. 문서가 중복되거나 오래되었거나, 제목/본문 구조가 깨져 있거나, 권한 metadata가 빠져 있으면 모델을 바꿔도 품질이 크게 좋아지지 않는다.

실무에서는 다음을 특히 신경 써야 한다.

1. 문서 수집과 인덱싱을 자동화한다.
2. 문서 삭제와 권한 변경이 검색 인덱스에도 반영되게 한다.
3. 검색 결과에 source, version, updated_at을 포함한다.
4. 답변할 근거가 없으면 "모르겠다" 또는 "문서에서 찾지 못했다"고 답하게 한다.
5. 검색 품질과 답변 품질을 분리해서 평가한다.
6. 민감 문서에는 tenant, role, owner 같은 metadata filter를 적용한다.
7. 외부 문서의 prompt injection 지시를 따르지 않도록 시스템 프롬프트와 후처리를 설계한다.

백엔드 면접에서는 RAG를 "AI 기능"으로만 말하기보다, 검색 시스템, 데이터 동기화, 권한 제어, 캐싱, 평가/모니터링까지 연결해서 설명하면 좋다.

## 꼬리 질문과 답변

### 1. RAG와 파인튜닝은 무엇이 다르고 언제 각각 쓰는가?

**답변**

RAG는 외부 문서를 검색해 프롬프트 컨텍스트로 넣는 방식이고, 파인튜닝은 모델의 파라미터를 추가 학습해 특정 출력 패턴이나 태스크 수행 능력을 맞추는 방식이다. 자주 바뀌는 사실, 사내 문서, 출처가 필요한 답변은 RAG가 적합하다. 반대로 말투, 형식, 분류 기준, 특정 작업 절차를 모델이 안정적으로 따르게 만들고 싶다면 파인튜닝이 유리하다. 실무에서는 둘 중 하나만 고르기보다 RAG로 지식을 제공하고 파인튜닝이나 프롬프팅으로 답변 스타일과 태스크 수행 방식을 맞추는 조합도 많이 쓴다.

### 2. RAG의 핵심 파이프라인 3단계는 무엇인가?

**답변**

RAG의 핵심 파이프라인은 Indexing, Retrieval, Generation이다. Indexing은 문서를 수집, 정제, chunking, embedding해서 검색 저장소에 넣는 단계다. Retrieval은 사용자 질문과 관련 있는 chunk를 vector search, keyword search, metadata filter, reranking으로 찾는 단계다. Generation은 검색된 근거를 프롬프트에 넣고 LLM이 답변을 생성하는 단계이며, 이때 근거 부족, context overflow, prompt injection 같은 문제가 생길 수 있다.

### 3. RAG에서 벡터DB 검색 품질을 높이는 방법에는 무엇이 있는가?

**답변**

먼저 문서를 의미 단위로 잘 나누는 chunking 전략이 중요하다. 제목, 섹션, 표, 코드 블록을 고려하지 않고 고정 길이로만 자르면 검색 결과의 맥락이 끊길 수 있다. 또한 metadata filter, hybrid search, query rewriting, multi-query retrieval, reranking을 조합하면 recall과 precision을 함께 개선할 수 있다. 마지막으로 실제 사용자 질문과 정답 근거 문서로 evaluation set을 만들어 Recall@k, MRR, nDCG 같은 지표를 지속적으로 측정해야 한다.

### 4. RAG 시스템에서 잘못된 답변이 나왔을 때 어디를 디버깅해야 하는가?

**답변**

먼저 검색 결과에 정답 근거 문서가 포함됐는지 확인해야 한다. 정답 문서가 없으면 indexing, chunking, embedding, metadata filter, query rewriting 문제일 가능성이 크다. 정답 문서는 검색됐는데 답변이 틀렸다면 prompt 구성, context 정렬, 모델 지시문, generation 단계의 hallucination 문제를 봐야 한다. 즉, RAG 디버깅은 "검색 실패인지 생성 실패인지"를 먼저 분리하는 것이 핵심이다.

### 5. 실무 서비스에서 RAG를 운영할 때 가장 조심해야 할 점은 무엇인가?

**답변**

가장 중요한 것은 데이터 최신성, 권한 관리, 평가 체계다. 문서가 삭제되거나 권한이 바뀌었는데 인덱스가 그대로면 오래된 정보나 민감 정보가 답변에 섞일 수 있다. 또한 검색 결과가 항상 정답이라는 보장이 없기 때문에, 근거 문서가 없을 때 답변을 거부하는 정책과 출처 표시가 필요하다. 운영 관점에서는 인덱싱 실패율, 검색 hit rate, 답변 근거 충실도, 사용자 피드백을 모니터링해야 한다.
